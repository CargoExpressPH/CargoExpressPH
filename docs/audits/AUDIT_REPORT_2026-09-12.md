## Executive summary

The application builds successfully, its public responsive browser flows pass, all 156 migrations that existed before this corrective change matched the deployed migration history, all 16 Edge Functions compile, and the current production data passed the read-only integrity checks performed during this audit. No known vulnerable production dependency was reported by `npm audit`.

The confirmed **High** payment defect has now been corrected in a forward-only local migration. Discount-aware totals had been added to pickup and ledger logic, but the manual delivery and additional-payment RPCs still compared payments with the original gross shipping cost. The new migration makes both RPCs use the shared payable calculation; adds locked server-side overpayment and method guards; binds idempotency keys to their order; and enforces delivery lifecycle/proof requirements at the database boundary. It has not been applied remotely.

Six additional confirmed defects were also fixed locally. The migration and two Edge Function fixes have not been deployed. Authenticated browser coverage could not run because the configured admin test account is no longer valid, and the repository's full E2E suite is state-changing while the configured backend is production. No production records, uploads, or configuration were changed.

## Architecture and services

- Frontend: React 19 SPA, React Router 7, Vite 6, PWA/service worker, JavaScript/JSX.
- Hosting: Vercel-oriented static frontend deployment.
- Backend: Supabase PostgreSQL/PostgREST, Auth, Realtime, Storage, database functions/triggers/RLS, and 16 Deno Edge Functions. There is no conventional Node backend server.
- Payments: PayMongo GCash sources, server-side capture/reconciliation, webhooks, and an idempotent payment ledger.
- Notifications: database-backed in-app notifications, Firebase Cloud Messaging, Web Push/VAPID, and scheduled delivery jobs.
- Email: Resend-backed announcement/email functions.
- Images: Supabase Storage with a Firebase/Firestore fallback path and storage-health monitoring.
- Maps/UI: Leaflet/React Leaflet; Framer Motion; html2pdf.js; dnd-kit.

## Findings and changes

### 1. Discounted manual settlement uses gross cost

- Severity: **High**
- Status: **Fixed locally — migration deployment pending**
- Affected modules: the stale definitions originated in `supabase/migrations/20260909030000_manual_payment_hardening.sql`; the correction is `supabase/migrations/20260912010000_discount_aware_manual_settlement.sql`, covering `record_delivery_payment` and `record_additional_payment`.
- Root cause: the later discount migrations made the ledger trigger, pickup RPC, order totals, and reports call `order_payable_amount(shipping_cost, discount_amount)`, but these two earlier RPC definitions still compare against `shipping_cost`.
- Impact:
  - At delivery, collecting the exact discounted balance can still produce a phantom gross balance and require a promise date or reject completion.
  - An exact manual additional settlement can be stored with transaction status `partial`, which the customer payment history displays incorrectly.
- Change: replaced every gross comparison/projected remainder with `order_payable_amount`, preserved atomic row locking, rejected unsupported/unverified delivery payment methods, enforced the existing no-overpayment rule server-side, and made duplicate-reference races fail instead of silently doing nothing. The final review also bound idempotency retries to the original order and moved the existing `Out for Delivery` plus 1–3 proof-photo requirements from UI-only enforcement into the RPC.
- Test result: **Passed — 92/92 shipping-discount/manual-settlement assertions**. New tests cover exact discounted delivery without a promise date, discounted shortfall rollback/promise handling, fully paid and unpaid delivery, negative values, exact and partial additional payments, both overpayment paths, retry and cross-order idempotency, role/method/verification/lifecycle/proof guards, repeat migration execution, and no-discount behavior.

### 2. Test harness globally disabled TLS certificate verification

- Severity: **High**
- Status: **Fixed locally**
- Affected files: `tests/helpers/config.js`, `tests/helpers/db.js`.
- Root cause: both helpers set `NODE_TLS_REJECT_UNAUTHORIZED=0`, causing authenticated test credentials to be transmitted without certificate verification.
- Change: removed both overrides. Environments with an interception proxy must install the proper CA (for example through `NODE_EXTRA_CA_CERTS`) instead.
- Test result: **Passed** for static/build regression; authenticated execution remains blocked by the stale admin account.

### 3. Payment history silently omitted orders after the first 200

- Severity: **Medium**
- Status: **Fixed locally**
- Affected files: `src/pages/customer/PaymentHistoryPage.jsx`, `src/lib/database.js`.
- Root cause: the page truncated the order list to 200 to avoid an oversized `.in()` URL, making older payment months appear genuinely empty.
- Change: load every order, chunk transaction requests into deduplicated batches of 100 IDs, page each chunk past the PostgREST row cap with stable ordering, and apply the loading timeout to both the order and transaction phases.
- Test result: **Passed** build/static regression; **Needs Manual Testing** with a customer over 200 orders or a generated staging fixture.

### 4. Trip creation hid auto-assignment failures

- Severity: **Medium**
- Status: **Fixed locally**
- Affected files: `src/lib/database.js`, `src/pages/admin/CreateTripPage.jsx`.
- Root cause: errors from reading pending bookings or updating matching bookings were ignored, then the UI always displayed “Trip created successfully.” Activity-log promises were also not awaited inside their error handlers.
- Change: preserve the valid created trip, return a partial-success warning when auto-assignment fails or a candidate changes concurrently, display that warning, compare-and-set the original pending/unassigned route state, and await individual activity-log writes so failures are actually caught.
- Test result: **Passed** build/static regression; **Needs Manual Testing** with an authenticated staging admin and an induced assignment failure.

### 5. Customer payment guidance contradicted enforced cash policy

- Severity: **Low**
- Status: **Fixed locally**
- Affected file: `src/pages/customer/PaymentHistoryPage.jsx`.
- Root cause: help copy said cash was accepted at delivery while UI and database logic correctly reject cash after pickup.
- Change: state that cash is accepted at pickup and later balances are settled through GCash.
- Test result: **Passed** build/static regression.

### 6. Public inquiry endpoint accepted malformed optional email

- Severity: **Low**
- Status: **Fixed locally; deployment pending**
- Affected file: `supabase/functions/submit-inquiry/index.ts`.
- Root cause: server-side email syntax was validated only when marketing opt-in was true, so a crafted request could save an invalid email for an ordinary inquiry.
- Change: validate any supplied string email, reject non-string crafted values with a clear 400 response, and persist the trimmed form.
- Test result: **Passed** Edge Function compilation; **Needs Manual Testing** after deployment with malformed, blank, phone-only, valid-email, and opt-in requests.

### 7. Photo fallback endpoint could expose provider error details

- Severity: **Low**
- Status: **Fixed locally; deployment pending**
- Affected file: `supabase/functions/get-photo-fallback/index.ts`.
- Root cause: provider errors and caught exception messages were returned verbatim to anonymous/authenticated callers.
- Change: log limited server-side diagnostics and return stable public messages while retaining the HTTP status.
- Test result: **Passed** Edge Function compilation and photo-fallback contract test; **Needs Manual Testing** after deployment against a forced provider failure.

## Remaining risks and unfinished problems

### Server-side business invariants

- **Medium — admin cancellation bypass/race:** `cancelOrderAsAdmin` re-fetches status but performs a later direct update. The database guard does not encode the same cutoff for admins. A direct authenticated admin API call or a status change between read and write can cancel an already-dispatched/delivered order. A locked RPC should validate and update atomically. This needs a migration and confirmation that the current cancellation cutoff is the intended permanent rule.
- **Medium — guest-booking ownership race:** `assignOrderToCustomer` checks the current owner's role and then performs an unconditional later update. Concurrent admins or a direct API caller can bypass “guest bookings only.” A locked/CAS RPC should verify the target role and current ownership atomically. This needs a migration.
- **Medium — forgeable chatbot identity:** the database intentionally permits a customer to insert `sender_role='bot'` because bot replies are generated in the browser. A customer can therefore forge bot-authored content in their own conversation. The durable fix is to generate bot messages server-side or cryptographically/server-authoritatively label them; that is an architectural change.
- **Low — CMS lost updates:** coverage/company JSON uses read-modify-write without a version/CAS condition. Concurrent admins can overwrite one another's edits.

### Operational and test risks

- **High — production-linked E2E configuration:** the local configuration targets the production Supabase project while the full E2E suite is explicitly state-changing. Create a separate staging project and make the suite refuse production project IDs/hosts.
- **Medium — authenticated regression gap:** stale admin credentials blocked 280 admin/customer checks. Replace the test account only in a staging environment; do not reset a real administrator.
- **Medium — provider paths not proven live:** GCash redirect/capture/webhook, real push delivery, Resend delivery, and upload/fallback failover need controlled staging tests and provider dashboards/logs.
- **Low — schema snapshot drift:** `supabase/schema.sql` does not contain all late discount/idempotency definitions even though all migrations are present and remote parity is exact. Regenerate/document the snapshot to keep audits from reading stale function bodies.
- **Low — bundle performance:** production build succeeds but `vendor-react` is approximately 527 kB minified and exceeds Vite's 500 kB warning threshold; the configured `vendor-pdf` chunk is empty. Review manual chunking and PDF lazy loading.
- **Low — dead data-access exports:** direct `recordPaymentTransaction` and `bulkUpdateOrdersStatusByTrip` remain exported but unused; their old patterns conflict with the current atomic RPC/trigger design and could be accidentally reused.

## Manual staging checklist

Run each item as customer, admin, unauthenticated visitor, and—where applicable—the wrong customer. Repeat submits, throttle the network, abort requests, and inject 400/401/403/409/429/500 responses.

- Auth: register, duplicate email, malformed fields, legal consent, confirmed/unconfirmed login, wrong password, reset link, change password/email, refresh, offline logout, cross-role routes.
- Profile: edit each address/contact field, invalid/blank values, concurrent save, refresh/relogin persistence, forbidden role/email mutation.
- Booking: valid booking, no trip, expired trip, mismatched route, duplicate click, offline/timeout retry, dirty-form navigation, cancellation request/approve/reject/direct unauthorized update.
- Admin trip/order: create duplicate route/day, auto-assign success/partial failure, capacity boundary, unweighed order, reassign trip, every allowed/forbidden status transition, guest ownership assignment race.
- Payment: cash pickup, verified/unverified manual GCash, exact/partial/overpayment, retry/idempotency, duplicate reference across orders, discounted delivery exact balance, discounted additional exact balance, PayMongo cancel/fail/success/webhook replay/poll race.
- Notifications: in-app unread/read/delete, multiple devices, no device, denied permission, expired token, retryable provider failure, notification navigation target, announcement opt-in/out.
- Chat/inquiries: bot answer/escalation/reopen/resolve, customer/admin unread counts, paging/search/realtime, wrong-customer access, malformed/rate-limited inquiry, concurrent admin claim/resolve.
- Photos: invalid type/size/count, interrupted compression/upload, cleanup after later failure, fallback read as owner/admin/public/non-owner, missing provider document, proof required at pickup/delivery.
- Dashboards/reports/logs: totals against ledger, date/time-zone boundaries, discounts separated from revenue, empty/large datasets, pagination/filter/export, actor and before/after audit fields.
